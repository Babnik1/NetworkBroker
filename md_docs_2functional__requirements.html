Functional Requirements

1. Назначение системы

Network Broker — сетевой брокер сообщений, предназначенный для обмена сообщениями между несколькими клиентами по протоколу TCP.

Система реализует модель Publish/Subscribe (Pub/Sub). Клиенты подключаются к серверу, регистрируются или авторизуются, создают тематические каналы (топики), подписываются на интересующие топики и публикуют сообщения.

Брокер принимает команды клиентов, выполняет необходимые проверки и передаёт сообщения подписанным клиентам.

2. Пользователи системы

Основным пользователем системы является клиент брокера.

Клиент взаимодействует с сервером посредством TCP-соединения и отправляет текстовые команды.

Каждому подключению соответствует уникальный идентификатор сессии.

После успешной регистрации или авторизации сессия связывается с конкретным клиентом.

3. Основные функции

Система должна обеспечивать следующие возможности:

  • подключение клиентов к серверу;
  • регистрацию новых клиентов;
  • авторизацию существующих клиентов;
  • отключение клиентов;
  • создание топиков;
  • подписку клиентов на топики;
  • отписку клиентов от топиков;
  • публикацию сообщений;
  • маршрутизацию сообщений подписанным клиентам;
  • хранение информации о клиентах;
  • хранение информации о топиках и подписках;
  • журналирование работы приложения;
  • конфигурирование приложения.

4. Сетевое взаимодействие

4.1. Подключение клиента

Сервер должен принимать входящие TCP-соединения.

Для каждого нового соединения сервер:

  1. принимает TCP-сокет;
  2. назначает соединению уникальный SessionId;
  3. создаёт объект сессии;
  4. передаёт сессии брокер сообщений;
  5. запускает обработку соединения.

Сервер должен поддерживать одновременное существование нескольких клиентских соединений.

4.2. Идентификация сессии

Каждое клиентское соединение имеет уникальный идентификатор сессии.

SessionId используется брокером для определения клиента, выполняющего команду.

5. Регистрация клиента

Клиент должен иметь возможность зарегистрироваться в системе посредством команды:

REGISTER <name>

При успешной регистрации:

  1. клиент создаётся в хранилище;
  2. клиент подключается к текущей сессии;
  3. сессия связывается с зарегистрированным клиентом;
  4. клиент получает ответ:
OK

Если клиент с указанным именем уже существует, сервер должен вернуть соответствующую ошибку.

6. Авторизация клиента

Существующий клиент должен иметь возможность подключиться к серверу посредством команды:

LOGIN <name>

При успешной авторизации клиент связывается с текущей сессией.

Если клиент не существует, должна возвращаться ошибка Client not found.

Если клиент уже подключён к другой сессии, должна возвращаться ошибка Client already connected.

7. Создание топика

Авторизованный клиент должен иметь возможность создать топик:

CREATE <topic>

Создатель топика автоматически становится его подписчиком.

Информация о созданном топике должна сохраняться в хранилище топиков.

Неавторизованный клиент не должен иметь возможность создавать топики.

8. Подписка на топик

Авторизованный клиент может подписаться на существующий топик:

SUBSCRIBE <topic>

После успешной подписки идентификатор клиента добавляется в список подписчиков топика.

Если топик не существует, клиент получает ошибку Topic not found.

Если клиент уже подписан на топик, возвращается соответствующая ошибка.

Информация о подписке сохраняется в хранилище топиков.

9. Отписка от топика

Авторизованный клиент может отказаться от подписки:

UNSUBSCRIBE <topic>

После успешной операции клиент удаляется из списка подписчиков топика.

Информация об изменении подписки сохраняется в хранилище.

10. Публикация сообщения

Авторизованный клиент может опубликовать сообщение:

PUBLISH <topic> <message>

При публикации система должна:

  1. определить клиента, отправившего сообщение;
  2. проверить наличие топика;
  3. получить список подписчиков топика;
  4. передать сообщение клиентам из списка подписчиков.

Если топик не существует, возвращается ошибка Topic not found.

Сообщение должно передаваться всем клиентам, подписанным на соответствующий топик.

11. Маршрутизация сообщений

Брокер отвечает за маршрутизацию сообщений.

При получении сообщения брокер не должен самостоятельно управлять сетевыми соединениями клиентов. Для отправки сообщения используется менеджер клиентов.

Общая схема:

Publisher
|
v
MessageBroker
|
v
TopicManager
|
v
список подписчиков
|
v
ClientManager
|
v
Subscriber Sessions

12. Проверка авторизации

Операции:

  • CREATE;
  • SUBSCRIBE;
  • UNSUBSCRIBE;
  • PUBLISH

должны выполняться только авторизованными клиентами.

При выполнении команды брокер получает ClientId, соответствующий SessionId.

Если соответствующий клиент не найден, операция считается выполненной неавторизованным клиентом и возвращается:

ERROR You are unauthorized

13. Отключение клиента

При отключении клиента менеджер клиентов должен удалить связь между сессией и клиентом.

После отключения клиент может повторно авторизоваться с новой сессии.

14. Хранение данных

Система должна сохранять информацию между запусками приложения.

На текущем этапе используются JSON-файлы.

14.1. Клиенты

В хранилище клиентов сохраняется информация о зарегистрированных клиентах.

14.2. Топики

В хранилище топиков сохраняются:

  • имена топиков;
  • идентификаторы клиентов, подписанных на каждый топик.

Репозитории скрывают формат хранения от менеджеров.

15. Команды протокола

Поддерживаются следующие команды:

Команда Назначение
REGISTER <name> Регистрация клиента
LOGIN <name> Авторизация клиента
CREATE <topic> Создание топика
SUBSCRIBE <topic> Подписка на топик
UNSUBSCRIBE <topic> Отписка от топика
PUBLISH <topic> <message> Публикация сообщения

16. Ответы сервера

При успешном выполнении операции сервер возвращает:

OK

При ошибке сервер возвращает сообщение с описанием причины.

Предусмотрены следующие типы ошибок:

ERROR Client not found
ERROR Client already exists
ERROR Client already connected
ERROR Invalid command
ERROR Topic not found
ERROR Already subscribed
ERROR You are unauthorized
ERROR Internal error

17. Обработка некорректных команд

Система должна обнаруживать:

  • неизвестные команды;
  • отсутствие аргументов;
  • отсутствие имени клиента;
  • отсутствие имени топика;
  • отсутствие сообщения при публикации;
  • некорректный формат команды.

В таких случаях клиенту возвращается:

ERROR Invalid command

18. Конфигурация

Параметры приложения должны задаваться через конфигурацию.

Конфигурация используется для задания параметров запуска приложения, в том числе сетевых параметров сервера и параметров журналирования.

19. Журналирование

Приложение должно вести журнал работы.

Логирование выполняется асинхронно: сообщения помещаются в очередь, после чего отдельный поток Logger извлекает их и записывает в файл.

Журнал должен содержать информацию о значимых событиях приложения, включая:

  • запуск сервера;
  • остановку сервера;
  • подключение клиентов;
  • ошибки сетевого взаимодействия;
  • ошибки работы с данными;
  • операции брокера.

20. Многопользовательская работа

Система должна поддерживать одновременную работу нескольких клиентов.

Для каждого клиента создаётся отдельная сессия.

Состояние клиентов и топиков централизованно управляется соответствующими менеджерами.

21. Клиентское приложение

В состав проекта входит консольный клиент BrokerClient.

Клиент предназначен для ручного взаимодействия с сервером и отправки команд по TCP.

Клиент является вспомогательным приложением и не содержит бизнес-логику брокера.

22. Требования к тестированию

Проект должен содержать автоматические тесты основных компонентов системы.

Тестированию подлежат:

  • репозитории;
  • ClientManager;
  • TopicManager;
  • MessageBroker;
  • отдельные сценарии взаимодействия компонентов.

Интеграционные тесты должны проверять работу нескольких компонентов совместно, в частности сценарии регистрации клиентов, создания топиков, подписки, отписки и публикации сообщений.

23. Нефункциональные требования

Производительность

Система должна поддерживать одновременное обслуживание нескольких TCP-клиентов без необходимости создания отдельного процесса для каждого клиента.

Расширяемость

Работа с данными должна быть отделена от бизнес-логики посредством интерфейсов репозиториев.

Это позволяет заменить JSON-хранилище другим типом хранилища без изменения основной логики брокера.

Надёжность

Ошибки выполнения команд не должны приводить к аварийному завершению всего приложения.

Документируемость

Исходный код должен сопровождаться документацией Doxygen.

Документация должна автоматически генерироваться в рамках CI/CD.

24. Ограничения текущей версии

В текущей версии проекта:

  • основное хранилище реализовано на JSON-файлах;
  • клиент является консольным;
  • протокол взаимодействия использует текстовые команды;
  • сервер реализован на Boost.Asio;
  • авторизация основана на имени клиента;
  • отсутствует отдельная система паролей и учётных данных;
  • брокер не предоставляет собственный GUI;
  • масштабирование на несколько серверных экземпляров не предусмотрено.

Данные ограничения не являются архитектурными препятствиями для дальнейшего развития системы.
