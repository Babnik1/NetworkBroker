2. Основные подсистемы

Проект разделён на следующие подсистемы:

src/
├── broker/
├── clients/
├── configurator/
├── db/
├── logs/
├── server/
└── topics/

server

Отвечает за сетевое взаимодействие:

  • TCP-сервер;
  • приём соединений;
  • создание сессий;
  • управление жизненным циклом соединений.

broker

Содержит бизнес-логику брокера сообщений.

Основной класс:

MessageBroker

Он является связующим компонентом между клиентами, топиками и сетевыми сессиями.

clients

Содержит:

  • модель клиента;
  • менеджер клиентов;
  • интерфейс менеджера клиентов.

topics

Содержит:

  • менеджер топиков;
  • интерфейс менеджера топиков;
  • управление подписками.

db

Содержит репозитории для хранения данных.

Текущая реализация использует JSON.

logs

Отвечает за журналирование приложения.

configurator

Отвечает за загрузку и обработку конфигурации приложения.

3. Server

Server является точкой входа сетевых соединений.

Он содержит:

boost::asio::io_context
boost::asio::ip::tcp::acceptor

При запуске сервера вызывается:

Server::Start()
|
+-- DoAccept()
|
+-- ioContext.run()

DoAccept() выполняет асинхронное ожидание входящего TCP-соединения.

После подключения клиента:

  1. создаётся новый Session;
  2. ему назначается SessionId;
  3. сессия добавляется в список активных сессий;
  4. сессии передаётся MessageBroker;
  5. запускается обработка сессии.

4. Session

Session представляет отдельное клиентское TCP-соединение.

Сессия отвечает за сетевой уровень взаимодействия с конкретным клиентом.

У сессии имеются:

  • идентификатор сессии;
  • TCP socket;
  • ссылка на брокер.

Упрощённо взаимодействие выглядит следующим образом:

TCP socket
|
▼
Session
|
▼
MessageBroker::HandleCommand()

Сессия не должна содержать бизнес-логику работы с клиентами или топиками.

Это позволяет отделить транспортный уровень от логики брокера.

5. MessageBroker

MessageBroker является центральным компонентом бизнес-логики.

Он получает от сессии:

  • SessionId;
  • команду клиента;
  • слабую ссылку на сессию.

Основной метод:

HandleCommand(
SessionId id,
const std::string& command,
SessionWeakPtr session
)

Метод:

  1. разбирает текстовую команду;
  2. определяет действие;
  3. проверяет необходимые аргументы;
  4. вызывает соответствующий метод брокера;
  5. преобразует результат в текстовый ответ клиенту.

6. Обработка команд

Поддерживаемые действия представлены перечислением Actions:

LOGIN
REGISTER
PUBLISH
SUBSCRIBE
CREATE
UNSUBSCRIBE

Команды сопоставляются с действиями посредством unordered_map.

Пример:

"LOGIN" -> LOGIN
"REGISTER" -> REGISTER
"PUBLISH" -> PUBLISH
"SUBSCRIBE" -> SUBSCRIBE
"CREATE" -> CREATE
"UNSUBSCRIBE" -> UNSUBSCRIBE

После определения действия MessageBroker вызывает соответствующий обработчик.

7. ClientManager

ClientManager отвечает за состояние клиентов.

Он управляет:

  • регистрацией;
  • подключением;
  • отключением;
  • поиском клиента по SessionId;
  • удалением клиента;
  • передачей сообщений клиентским сессиям.

Основные операции:

CreateClient()
ConnectClient()
DisconnectClient()
GetClientId()
SendTopicMessage()
RemoveClient()

Менеджер хранит клиентов в памяти:

unordered_map<ClientId, Client>

Также менеджер содержит интерфейс репозитория клиентов.

8. TopicManager

TopicManager отвечает за топики и подписки.

Основное состояние:

unordered_map<
Topic,
unordered_set<ClientId>
>

Таким образом, каждому топику соответствует множество клиентов.

Например:

sports
├── Client 1
├── Client 3
└── Client 7
news
├── Client 2
└── Client 3

Основные операции:

Create()
Subscribe()
Unsubscribe()
Publish()

9. Репозитории

Для отделения хранения данных от бизнес-логики используется Repository Pattern.

Менеджеры работают с интерфейсами:

IClientRepository
ITopicRepository

Текущие реализации:

JsonRepository
JsonTopicRepository

Данные хранятся в:

clients.json
topics.json

Архитектура позволяет заменить JSON-репозитории, например, на SQLite:

ClientManager
|
v
IClientRepository
|
+---- JsonRepository
|
+---- SqliteClientRepository

Аналогично для топиков.

12. Слабая ссылка на Session

MessageBroker получает:

SessionWeakPtr

вместо владения объектом Session.

Это позволяет избежать создания циклической зависимости владения между брокером и сессией.

Сессия владеет или использует брокер, а брокер при необходимости может получить временный shared_ptr из weak_ptr.

13. Управление памятью

Для управления временем жизни объектов используются умные указатели:

std::shared_ptr
std::unique_ptr
std::weak_ptr

Основные случаи использования:

Тип Назначение
shared_ptr совместное владение менеджерами, сессиями и брокером
unique_ptr исключительное владение объектами
weak_ptr ссылка на Session без владения

14. Логирование

Подсистема логирования вынесена в отдельный модуль.

Архитектура логирования:

Application threads
|
| log message
▼
Log queue
|
▼
Logger thread
|
▼
app.log

Основной принцип — отделить формирование логов от записи на диск.

Метод Logger::Log() работает в отдельном потоке и извлекает сообщения из очереди.

Таким образом, операции записи в файл не выполняются непосредственно вызывающим кодом.

15. Синхронизация Logger

Очередь сообщений логгера защищается mutex.

Рабочий поток:

  1. проверяет состояние очереди;
  2. блокирует mutex;
  3. извлекает сообщение;
  4. освобождает mutex;
  5. записывает сообщение в файл.

При отсутствии сообщений поток временно засыпает.

Завершение работы выполняется после установки флага остановки и обработки оставшихся сообщений.

16. Конфигурация

Конфигурация вынесена в отдельную подсистему configurator.

Это позволяет не смешивать параметры приложения с бизнес-логикой.

Конфигурация загружается при запуске приложения и используется компонентами, которым необходимы соответствующие параметры.

21. Архитектурные принципы

В проекте используются следующие принципы:

Разделение ответственности

Сетевой код, бизнес-логика, управление клиентами, управление топиками и хранение данных находятся в отдельных компонентах.

Dependency Inversion

Бизнес-логика работает с интерфейсами репозиториев:

IClientRepository
ITopicRepository

а не непосредственно с JSON-файлами.

Repository Pattern

Работа с постоянным хранилищем вынесена в отдельные классы репозиториев.

Manager Pattern

Управление состоянием клиентов и топиков выполняется специализированными менеджерами.

Асинхронное сетевое взаимодействие

Для сетевого уровня используется Boost.Asio и io_context.

Разделение транспорта и бизнес-логики

Session отвечает за TCP-взаимодействие, а MessageBroker — за обработку команд и бизнес-правила.

22. Возможности дальнейшего развития

Архитектура позволяет расширить систему без существенной переработки существующих компонентов.

Возможные направления:

  • переход с JSON на SQLite/PostgreSQL;
  • полноценная аутентификация с паролями;
  • TLS;
  • бинарный или структурированный протокол;
  • асинхронные очереди сообщений;
  • полноценная многопоточная обработка io_context;
  • сохранение истории сообщений;
  • QoS;
  • wildcard-топики;
  • административный интерфейс;
  • распределённый брокер;
  • кластеризация нескольких серверов.

При этом базовая структура:

Server
↓
Session
↓
MessageBroker
↓
Managers
↓
Repositories

может быть сохранена.
